### Manual verification

Everything below ran against my own harness, not the Engineer's:

- Created `qa_driver.py` **outside the repo** (in the session scratchpad) doing
  `from web.main import app` and registering `/qa/http-error` (raises `requests.HTTPError`),
  `/qa/unhandled` (raises bare `Exception`), and a `/qa/probe` diagnostic route. No repo file
  was modified at any point.
- Copied `app.db` to the scratchpad and seeded `qa-042-valid` with `expires_at = now + 7200`.
  **Confirmed the Engineer's claim about the dev database:** the three pre-existing sessions
  in `app.db` expired 37-94 days ago (`expires_at - now` = -8122952, -3451151, -3227777 s).
- Ran `DB_PATH=<copy> PYTHONPATH=<scratchpad>:<repo> .venv/bin/uvicorn qa_driver:app --port 8942`.
  `GET /health` → `{"status":"ok"} [200]`.
- **Non-vacuity of the byte-identity check, proved two ways.** (a) `/qa/probe` returned
  `{"cookie": null}` without the cookie and `{"cookie": "qa-042-valid"}` with it, so the cookie
  demonstrably reaches the application on the same requests. (b) Stronger: `GET /` with that
  cookie returned **502**, while `GET /` with a garbage cookie (`session_id=not-a-session`)
  returned **200** with the logged-out nav. The app therefore genuinely resolves
  `qa-042-valid` as an authenticated session and proceeds to a Yahoo call — a handler that
  *did* derive had a real, resolvable user available to it and would have rendered differently.
- That 502 from `/` is itself the end-to-end proof of the ticket's purpose: an authenticated
  visitor whose real route fails on Yahoo lands on the new page. I confirmed it is the new
  page (`<title>Error</title>`, `Yahoo API request failed. Please try again.`, one
  "Back to home" occurrence) with `<nav>` anchors `NONE`.
- Walked the unaffected navs live: logged-out `/` and the three demo pages, link lists as
  recorded in the AC4 row.
