Two findings worth stating explicitly:

- **The critical pair stays distinguishable.** Empty context → `[]`; explicit
  `is_authenticated=False` → the login link. A bare `{% elif is_authenticated %}` would have
  collapsed these; the implementation keeps a separate `{% elif is_authenticated is undefined %}`
  ahead of it, so the distinction is structural, not incidental.
- **`auth_state_unknown` still wins where both could apply.** It is still the first `{% if %}`
  in the block (`web/templates/base.html:24`), ahead of `demo_mode` and both auth branches, and
  it is still keyed on its own name. Combining it with `is_authenticated=True` or `demo_mode=True`
  — each of which would otherwise produce links — still yields `[]`, so the branch is
  demonstrably winning rather than merely co-existing. It was not collapsed into the new
  default; the diff does not touch it.

### Manual verification

App started with `.venv/bin/python -m uvicorn web.main:app --port 8099`. Nav anchors scraped
from inside `<nav>…</nav>`:

- `/` (logged out) → **200**, nav = `["/auth/login"]`. Unchanged.
- `/demo/overview` → **200**, nav = `["/demo/overview", "/demo/waiver", "/demo/projection", "/auth/login"]`.
- `/demo/waiver` → **200**, same demo nav.
- `/demo/projection` → **200**, same demo nav.
- `/demo/overview/head-to-head` → **200**, same demo nav.

**What I could not verify, stated plainly:**

- **The authenticated pages were not walked in a browser.** `/overview`, `/waiver` and
  `/projection` each return `302 Found` with `location: /auth/login`, and `/auth/login` in turn
  302s to `https://api.login.yahoo.com/oauth2/request_auth?...`. Completing that requires a real
  Yahoo OAuth round trip through the ngrok tunnel, which I cannot drive; following the redirect
  chain programmatically returned 429 from Yahoo. So authenticated `/`, `/overview`, `/waiver`
  and `/projection` are **owner-must-verify**. The Engineer's account of this limitation is
  accurate — I hit the identical wall. What I can say is that these branches are exercised by
  real `TestClient` requests against inserted sessions with Yahoo mocked at the route module's
  namespace, those tests are green, and the AC4 probe proves their nav assertions are
  load-bearing. That is strong evidence, but it is not the running-app walk the Verification
  section asks for.
- **The error page was not exercised in the running app.** I could not hand-trigger the
  `requests.HTTPError` → 502 or the 500 handler; `/demo/overview/table?week=999` returns 200,
  `…/head-to-head/table?week=abc` returns FastAPI's 422, and `/nope` returns FastAPI's JSON 404
  (no header at all — pre-existing and unrelated). **Owner-must-verify.** What I did verify
  deterministically: both handlers in `web/main.py:50` and `:63` spread
  `**unknown_auth_shell_context()` into `error.html`, and rendering `error.html` with that
  context yields **zero** nav anchors. I additionally rendered `error.html` with *no* shell
  flags at all — it also yields zero anchors now, whereas before this ticket that same
  degraded render would have shown the full authenticated nav. So the flip makes the error
  page strictly safer, not riskier.
