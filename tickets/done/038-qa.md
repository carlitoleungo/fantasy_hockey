### Notes for the Reviewer

**1. The fix narrows write-path atomicity — reproduced, and confirmed harmless to the ACs.**
The Engineer flagged that `_merge_into_cache` reads outside the per-league write lock. I
forced the interleaving rather than reasoning about it (patched `cache.read` to stall one
thread between its read and its write):

| Implementation | Result of the forced interleaving |
|---|---|
| Pre-fix `cache.append` (read **inside** the lock) | weeks `[1, 2, 3]` on disk — nothing lost |
| Post-fix `_merge_into_cache` (read **outside** the lock) | weeks `[1, 2]` on disk — the other thread's week 3 was overwritten |

The lost week self-heals: the very next `get_matchups()` call re-derives `_last_cached_week`
as 2, re-fetches, and the file returns to `[1, 2, 3]`, 3 rows, 0 duplicates (observed, not
inferred). So: no bloat, no duplicates, no permanent loss, and **no acceptance criterion is
affected** — AC1/AC4 hold under every interleaving because every write writes an
already-deduplicated frame. That is why this is not a NEEDS FIXES. It is nonetheless a real
reduction in a guarantee ticket 037 established, and the ticket forbids the `data/cache.py`
change that would restore it, so it is a Reviewer/PM call whether to open a follow-up for a
`cache.merge_on(...)` primitive that holds the league lock across read and write.
Practical exposure is narrow (reasoning, not measured): two concurrent calls for one league
normally fetch the same week set, in which case the losing writer's frame already contains
those weeks; divergent fetch sets are needed to lose anything.

**2. `cache.append()` now has zero callers** in `data/`, `web/`, and `analysis/` — only
`tests/test_cache.py` still exercises it. Not a defect and out of this ticket's scope
(`data/cache.py` is off limits), but worth a decision on whether the primitive stays.

**3. Minor doc drift caused by this diff.** `docs/DECISIONS.md:248` cites
"`data/matchups.py` lines 44–46" for the unconditional `current_week` append. The module
docstring gained a line, so that block is now at lines 45–47. `docs/DECISIONS.md` is not in
`Touches`, so the Engineer was right not to touch it; flagging it for whoever can.

No pre-existing bugs surfaced during verification, so nothing was filed to
`docs/improvements.md`. No new `docs/LEARNINGS.md` entry: the "assert on disk, not through
the read-side dedup" lesson is specific to this cache/dedup pairing rather than a trap an
unrelated ticket would hit.
