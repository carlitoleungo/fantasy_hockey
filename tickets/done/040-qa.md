> **Harness warning for anyone repeating this.** My first pass produced a false result at line
> 241 — it reported `test_authenticated_head_to_head_renders_authenticated_nav` failing. The
> cause was Python bytecode caching, not the tests. Lines 174, 241 and 311 are all exactly 77
> bytes, so mutating 174 and then 241 yields two `overview.py` files of **identical size**, and
> with mtime landing in the same second CPython reused the stale `.pyc` from the previous probe.
> `pytest -p no:cacheprovider` does not prevent this. Purging `__pycache__` between iterations
> fixed it and all five then matched. Anyone re-running this probe must clear `__pycache__`
> between mutations or they will read the previous branch's result.

### Engineer's claim (a): on authenticated branches the nav assertion alone does not catch it — **CONFIRMED**

Tested by ablation. With `assert "Alpha League" in _header_left(response.text)` stubbed out and
each of lines 56, 146, 174 deleted in turn, the module returned **`32 passed`** every time — the
nav assertion catches nothing. With the mirror ablation (nav assertion stubbed, header assertion
kept), all three mutations failed as normal.

So on the three authenticated branches the header-label assertion is the **sole** guard, exactly
as reported. The mechanism is confirmed by `test_base_html_nav_branches[{}-expected0]`, which
asserts directly against the template that an empty context yields `AUTHENTICATED_NAV`. This
vindicates the ticket's insistence on both assertions in every test — a nav-only version of these
five tests would have been decorative.

### Engineer's claim (b): the `data.demo.get_matchups` patch target actually takes effect — **CONFIRMED**, by stronger evidence

The Engineer's argument (241 fails only `/demo/overview`, 311 fails only the head-to-head case,
therefore the patch landed) is sound but indirect. I proved it directly:

| Request | Response body size | Empty-state marker present |
|---|---|---|
| `/demo/overview`, unpatched | 23,194 bytes | no |
| `/demo/overview`, `patch("data.demo.get_matchups", return_value=None)` | **1,465 bytes** | **yes** ("No matchup data") |
| `/demo/overview`, `patch("web.routes.overview.get_matchups", return_value=None)` | 23,194 bytes — **byte-identical to unpatched** | no |
| `/demo/overview/head-to-head`, unpatched | 12,481 bytes | no |
| `/demo/overview/head-to-head`, `data.demo` patch | **1,602 bytes** | **yes** |
| `/demo/overview/head-to-head`, route-module patch | 12,481 bytes — **byte-identical to unpatched** | no |

The correct target collapses the body and surfaces the empty-state marker, so the demo tests
demonstrably render through the empty branch. The wrong target is a complete no-op.

I also ran the trap the ticket was written around as a control: substituting
`patch("web.routes.overview.get_matchups", …)` into `test_demo_empty_state_renders_demo_nav` and
then deleting line 241, and again line 311, produced **`2 passed`** both times. A wrong patch
target would have shipped two green tests guarding nothing. The Engineer picked the right target
and it is load-bearing.
