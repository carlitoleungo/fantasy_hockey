### AC4 adjudication — "omitted or `None`"

**AC4 is met.** The "omitted" half of the wording is not satisfiable without breaking a
different clause of the same ticket, and the AC's own worked examples are both the `None`
form.

Observed fact: `cache.read()` raises
`TypeError: read() missing 2 required positional arguments: 'league_key' and 'data_type'`.
So an omitted league is genuinely not expressible today.

Why implementing it would violate the ticket:

| Way to support an omitted league | What it breaks |
|---|---|
| Default `league_key=None` in place | Python forbids a non-default parameter after a defaulted one, so `data_type` and `df` would need defaults too, making `cache.write()` with zero arguments legal. That is "a function signature change visible to callers beyond accepting `None`/absent league", which the ticket's Out of scope forbids. |
| Reorder to `write(data_type, df, league_key=None)` | Every production call site passes `league_key` positionally, so this breaks AC4's own second clause ("every existing league-keyed call site is unchanged in behaviour"). |

The two clauses of AC4 are in direct tension, and the Engineer resolved it the only way
that keeps the rest of the ticket intact. The AC's parenthetical examples
(`cache.write(None, "some_type", df)` / `cache.read(None, "some_type")`) are implemented,
and I ran both myself. **Recommendation for the PM:** drop the word "omitted" from this
AC's phrasing in future tickets; it reads as an alternative but is unimplementable here.

### Notes

- **Pre-existing, out of scope, not a 037 regression:** during the route walk,
  `matchups.parquet` reached **48 rows** for a 3-team × 2-week dataset (6 unique rows), one
  6-row append per `get_matchups` call across 8 calls. This is the known append-per-page-load
  bloat that `docs/improvements.md` tracks and **ticket 038** owns; the ticket explicitly
  forbids touching `data/matchups.py` here. It is masked at read time by the
  `drop_duplicates(subset=["team_key", "week"], keep="last")` in `data/matchups.py:74`, and
  my check confirmed the deduplicated result was still correct (weeks `[1, 2]`). Already
  tracked, so I did not file a new `improvements.md` entry.
- **Residual concurrency gap, correctly out of scope:** `data/matchups.py` does an unlocked
  `_last_cached_week()` read and *then* calls `cache.append()`. Two concurrent
  `get_matchups` calls can both decide to fetch the same week and both append. `cache.append`
  itself is now atomic (AC1 holds), so this produces duplicate rows rather than lost or
  corrupt data, and the read-time dedup absorbs it. Cross-call atomicity is ticket 038's
  concern, not 037's.
- **Minor, cosmetic:** the lock registry keys `None` on the literal string `"_shared"`, so a
  league whose key were literally `_shared` would share a lock with the shared tier. Yahoo
  league keys are of the form `419.l.11111`, so this is unreachable. Not worth a fix; noting
  it for the Reviewer only.
- I did **not** independently verify the diff's file scope, because I was instructed not to
  run git. As a proxy, `find -mtime -3` shows `data/cache.py` (17:48) and
  `tests/test_cache.py` (17:47) as the two most recently modified files, with everything
  else dating to the earlier nav-shell work (16:44–16:46). That is consistent with the
  ticket's `Touches` list but is **not** a diff. **The Reviewer gate should confirm the
  actual diff scope.**
- Nothing new was added to `docs/LEARNINGS.md`: the atomic-rename and lock-registry patterns
  are already recorded in the two `docs/DECISIONS.md` 2026-07-23 entries this ticket
